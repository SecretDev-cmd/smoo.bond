Using binary files to run the server

You'll find binary files of recent server versions attached on its releases page.

  • Server is for GNU/Linux x64
  • Server.arm is for GNU/Linux ARM
  • Server.arm64 is for GNU/Linux ARM64
  • Server.exe is for Windows
Just execute them (preferable in a CLI) and you're running the server. On GNU/Linux you might need to install additional runtime dependencies (Debian/Ubuntu: libicu67).

If you don't trust those binaries or want to build a server version with your own changes, you can build the binary files from the source code: 

git  clone  https://github.com/Sanae6/SmoOnlineServer
cd  SmoOnlineServer
dotnet  publish  ./Server/Server.csproj  -c Release

Building it requires the .NET 6.0 SDK. The builded binary files for your system will be located at ./Server/bin/Release/net6.0/, you can change this path by using the -o parameter. To run your own builds you'll also need the .NET Runtime installed.

Alternatively you can build with --self-contained which allows you to run the binary on systems without the .NET Runtime. But that requires you to specify the runtime for which to build for (e.g. -r linux-x64, -r linux-arm, -r linux-arm64 or -r win-x64). If you're providing the runtime anyway consider also using -p:publishSingleFile=true to bundle everything into one single binary file.

An easier alternative to building it directly is to use Docker. That way the only required software you need to install on your system is Docker. All other dependencies will not be installed on your system directly but are only downloaded and used sandboxed. The source code of the server comes with an docker-build.sh script to easily trigger building the server:

  • ./docker-build.sh x64 to build a Server binary for GNU/Linux x64
  • ./docker-build.sh arm to build a Server.arm binary for GNU/Linux ARM
  • ./docker-build.sh arm64 to build a Server.arm64 binary for GNU/Linux ARM64
  • ./docker-build.sh win64 to build a Server.exe binary for Windows
  • ./docker-build.sh all to build the binaries for all systems
The builded server artifacts should be in the bin directory afterwards.

Using pre-build docker images with docker-compose to run the server

The server project provides ready to use docker images for different architectures (amd64, arm and arm64). They can be used in a lot of different scenarios together with different cloud or hosting providers. But you can also run them on your system on which you already installed docker.

One benefit of this is, that you don't have to deal with installing any Micro$oft dependencies on your system or need to build the project on your own. The server is also running isolated in its own container separated from the rest of the system.

Because plain docker commands become quite a hassle to use, one recommendation would be to use docker-compose to have all options inside a docker-compose.yml file: 

version: "3.7"

services:
  server:
    image: ghcr.io/sanae6/smo-online-server
    # build: .
    # user: 1000:1000
    stdin_open: true
    restart: unless-stopped
    ports:
    - 1027:1027
    volumes:
    - ./data/:/data/

When the file is present you can start the server by calling docker-compose up -d in the same directory. This will download and start the server in the background listening on port 1027 (external:internal) and create the settings.json file in the data sub directory. You'll also need to run this after making any changes to the docker-compose.yml.

The first time executing this will download the currently latest server version automatically. But once it downloaded it, it will stick to the version. If you want to update in the future you should call docker-compose pull && docker-compose up -d to update to newer versions. Alternatively in the docker-compose.yml after the image name, you can specify what version exactly you want to run, e.g. image: ghcr.io/sanae6/smo-online-server:1.0.2. Check out the GitHub repository for all available docker tags.

If you don't want to use a pre-build image but rather want to build the docker image yourself (e.g. with your own fixes to the source code), you can comment out the image line and comment in the build line in the docker-compose.yml. The build value needs to point to the server code directory that contains the Dockerfile. To rebuild after changes you'll need to execute docker-compose build && docker-compose up -d.

The restart: unless-stopped in the docker-compose.yml will automatically restart the server if it crashes or starts it again after a system reboot. To really stop the server you'll need to call docker-compose stop.

To attach to the server on the command line interface, to send commands to it, use docker attach `docker-compose ps -q` --sig-proxy=false. If you only want to look at the server logs without giving it any commands you can use docker-compose logs --tail=20 --follow.

For additional security on GNU/Linux it's advised to define which user should run the server (default: root). Comment in the user line in the docker-compose.yml and provide the user ID and group ID to use (execute echo $(id -u):$(id -g) to get your own IDs). You'll also need to modify the permissions of the data sub-directory, so that the user can write to it (chown 1000:1000 -R ./data/).

Configuring the server with the settings.json file
{
  "Server": {
    "Address": "0.0.0.0",
    "Port": 1027,
    "MaxPlayers": 8
  },
  "Flip": {
    "Enabled": true,
    "Players": [],
    "Pov": "both"
  },
  "Scenario": {
    "MergeEnabled": false
  },
  "BanList": {
    "Enabled": false,
    "Players": [],
    "IpAddresses": [],
    "Stages": [],
    "GameModes": []
  },
  "Discord": {
    "Token": null,
    "Prefix": "$",
    "CommandChannel": null,
    "LogChannel": null
  },
  "Shines": {
    "Enabled": true,
    "Excluded": [
      496
    ],
    "ClearOnNewSaves": false
  },
  "PersistShines": {
    "Enabled": false,
    "Filename": "./moons.json"
  },
  "JsonApi": {
    "Enabled": false,
    "Tokens": {}
  }
}

The settings.json file is automatically created when the server starts. At the right or above you can see the default values for server version 1.0.5.

  • Server:
    • Address: The network interface the server listens on for incoming connections. Leave it at "0.0.0.0" to accept incoming connections from all networks. There are very few and rare use cases where you'd ever want to change this value.
    • Port: The TCP port clients use to connect to the server. You need to change this for example, if you're running multiple servers on the same computer or want to avoid firewalls blocking this port. When using docker you should not edit the port here, but inside the docker-compose.yml.
    • MaxPlayers: Maximum amount of players that can be connected to the server at the same time. A value higher than 6 might currently cause lagging or crashing in Wooded Kingdom.
  • Flip: Visually flips the 3D (and 2D) models of players on their head.
    • Enabled: true or false.
    • Players: An array of unique profile IDs (not their names) of players which are on the flip list and therefore affected by this setting.
    • Pov: Affects who sees whom as flipped. Possible values: "self" (affected players will see unaffected players as flipped), "others" (affected players will be seen as flipped by everyone), or "both" (affected players will see everyone as flipped and everyone sees them as flipped).
      Note: you'll never see yourself as flipped.
  • Scenario:
    • MergeEnabled: true or false. When the players are in different stages of the story (scenarios), they are technically in different levels and don't see each other. This option tries to merge them virtually all together, so they can see each other without being in the same level.
  • BanList:
    • Enabled: true or false.
    • Players: An array of unique profile IDs (not their names) that are prevented from joining the server. For example you could enter "00000001-00000-0000-0000-000000000000" to prevent Ryujinx players to connect, that haven't changed their default profile yet.
    • IpAddresses: An array of IPv4 addresses that are prevented from joining the server.
    • Stages: 1.0.4 An array of values that result in a kick from the server when a player joins one of them.
    • GameModes: 1.0.5 An array of game mode indicies (integers) that result in a kick from the server when a player activates one of them.
  • Discord:
    • Token: Secret credential string with that the server can login to as the discord bot.
    • Prefix: Messages that start with this prefix string are interpreted by the bot as commands to it.
    • CommandChannel: 1.0.3 You can enter the unique ID of the Discord channel (between double quotes ") the bot should receive commands from but not send log messages to.
    • LogChannel: You can enter the unique ID of the Discord channel (between double quotes ") the bot should write log messages to and receive commands from.
  • Shines:
    • Enabled: 1.0.3 1.0.4 true or false. Can be used to disable moon synchronization between players.
    • Excluded: 1.0.5 An array of values that are excluded from being synchronized between players. By default the moon 496 is excluded because receiving it causes a soft lock where the Inverted Pyramid doesn't open up.
    • ClearOnNewSaves: 1.0.5 true or false. Enabling this will forget the collected moons that the server remembers when a player enters Cap Kingdom in scenario 1 (this means a new save file before entering Cascade Kingdom). This can be useful for co-op gameplay or speedruns.
  • PersistShines: 1.0.2 An option to save shines (moons) collected into a file, to survive server restarts and crashes.
    • Enabled: true or false.
    • Filename: In which file to save the shines into.
  • JsonApi: 1.0.5 An option to enable and configure the JSON API which can be used to fetch the server settings and current player status, or to execute commands remotely.
    • Enabled: true or false.
    • Tokens: An object that maps tokens (secret access codes) to an array of permissions.
Commands to control or interact with a running server
When running the server with the binary, attaching to the docker container, or using the Discord integration, you can send it commands to control and interact with it. Following are all the commands that the server version 1.0.5 understands.
help Outputs a list of all possible commands.
list Outputs the player names and profile IDs of all currently connected players.
loadsettings Reloads the modified settings.json in without restarting the server.
maxplayers <player-count> Sets the amount of players that can be connected to the server at the same time.
scenario {true|false} Enables or disables the scenario merging. See the settings section for details.
sendall <stage> Shortcut that will send all connected players to the given stage.
  • <stage>
    Invalid stage values (e.g. for custom kingdoms) can be send by appending a ! to the end.
send <stage> <warp-id> <scenario> <player>... Sends individual player(s) to a specific stage.
  • <stage>
    Invalid stage values (e.g. for custom kingdoms) can be send by appending a ! to the end.
  • <warp-id> change stage ID for the warp. To specify exactly where to spawn inside the stage. Use "" for the default spawn point (the Odyssey).
  • <scenario> What scenario to send the players to. Has to be an integer between -1 and 127. Use -1 to keep the scenario unchanged.
  • <player>... A list of players to send (separated by spaces). Can be their player name or their profile ID. * is also a valid value to send all connected players.
rejoin <player-name>... Closes the connection to the client of the player(s). The client will automatically reconnect again.
  • <player-name>... A list of player names to rejoin (separated by spaces). * is also a valid value for all connected players. If you start the list with !*, it will rejoin all but the following players.
crash <player-name>... Send the player(s) to an invalid stage that will crash the game, and then closes the connection to the client of the player(s).
  • <player-name>... A list of player names to crash (separated by spaces). * is also a valid value for all connected players. If you start the list with !*, it will crash all but the following players.
ban ... Commands to control who or what is banned on this server by adding it to the banlists (see settings).
ban list 1.0.4 Shows all entries on the banlists and whether they are enabled or not.
ban {enable|disable} 1.0.4 Enables or disables all banlists at once.
ban player <player-name>... 1.0.4 Sends the connected player(s) to an invalid stage that will crash the game, adds their profile IDs and IPv4 addresses to the banlists, and then ignores the connection to the client of the player(s).
  • <player-name>... A list of player names to ban (separated by spaces). * is also a valid value for all connected players. If you start the list with !*, it will ban all but the following players.
ban profile <profile-id> 1.0.4 Adds the profile ID to the banlist. If a player with that profile ID is connected, then it sends them to an invalid stage that will crash the game, and then ignores the connection to the client of the player.
  • <profile-id> The unique profile ID of the player (not its name) that should be banned from the server.
ban ip <ipv4-address> 1.0.4 Adds the IPv4 address to the banlist. If a player with that IPv4 address is connected, then it sends them to an invalid stage that will crash the game, and then ignores the connection to the client of the player.
  • <ipv4-address> The IPv4 address that should be banned from the server.
ban stage <stage> 1.0.4 Adds the stage to the banlist. If a player enters a banned stage, then it sends them to an invalid stage that will crash the game, and then ignores the connection to the client of the player.
  • <stage>
    Using an alias will add all known stages in that kingdom to the banlist individually.
    Invalid stage values (e.g. for custom kingdoms) can be added by appending a ! to the end.
ban gamemode <game-mode> 1.0.5 Adds game modes to the banlist. If a player enters a banned game mode, then it sends them to an invalid stage that will crash the game, and then ignores the connection to the client of the player.
  • <game-mode> The index that the mod uses for the game mode or its identifier.
    • -1 or None: No active game mode.
    • 0 or Legacy: Used by older mod versions from before the game mode was synchronized.
    • 1 or HideAndSeek: Hide & Seek
    • 2 or Sardines: Sardines
    • 3 or FreezeTag: Freeze-Tag
unban ... Commands to remove entries from the banlists (see settings).
unban profile <profile-id> 1.0.4 Removes the profile ID from the banlist.
  • <profile-id> The unique profile ID of the player (not its name) that should no longer be banned from the server.
unban ip <ipv4-address> 1.0.4 Removes the IPv4 address from the banlist.
  • <ipv4-address> The IPv4 address that should no longer be banned from the server.
unban stage <stage> 1.0.4 Removes the stage from the banlist.
  • <stage>
    Using an alias will remove all known stages in that kingdom from the banlist individually.
    Invalid stage values (e.g. for custom kingdoms) can be removed by appending a ! to the end.
unban gamemode <game-mode> 1.0.5 Removes the game mode from the banlist.
  • <game-mode> The index that the mod uses for the game mode or its identifier.
    • -1 or None: No active game mode.
    • 0 or Legacy: Used by older mod versions from before the game mode was synchronized.
    • 1 or HideAndSeek: Hide & Seek
    • 2 or Sardines: Sardines
    • 3 or FreezeTag: Freeze-Tag
tag ... Hide & Seek helper commands.
tag time <player-name> <minutes> <seconds> Manually sets the Hide & Seek timer for a player.
  • <player-name> One specific player name or * for all connected players.
  • <minutes> Value between 0 and 65535.
  • <seconds> Value between 0 and 59.
tag seeking <player-name> {true|false} Manually sets the Hide & Seek status for a player to seeker (true) or hider (false).
  • <player-name> One specific player name or * for all connected players.
tag start <seconds> <player-name>... Starts a countdown that will set the Hide & Seek status of all connected players when the time is over.
  • <seconds> Value between 0 and 255.
  • <player-name>... A list of player names that will be seekers. Everyone else will become hiders.
flip ... Commands to control the flip feature (see settings).
flip list Lists all profile IDs that are on the flip list.
flip set {true|false} Enables or disables the flip feature.
flip pov {both|self|others} Sets the setting for who sees whom as flipped.
flip add <profile-id> Adds a player to the flip list.
  • <profile-id> The unique profile ID of the player (not its name) that should be added to the flip list.
flip remove <profile-id> Removes a player from the flip list.
  • <profile-id> The unique profile ID of the player (not its name) that should be added to the flip list.
shine ... commands to manipulate shines (moons).
shine list Lists all shine IDs that have been collected globally by all players.
shine clear Removes all saved shines on the server. This will not remove shines in-game from connected players.
shine sync Manually syncs all saved shines to all connected players. Only those shines that are missing for the player from the point of view of the server are transferred. This will not remove shines in-game from connected players. This should normally happen automatically when entering the game, when there's a change to the shines and every two minutes.
shine send <shine-id> <player-name>... Manually sends one shine to players.
  • <shine-id> The unique ID for an individual shine (moon) in the game.
  • <player-name>... A list of player names that shall receive the shine (separated by spaces). * is also a valid value for all connected players.
shine set {true|false} 1.0.3 To enable or disable shine syncing.
shine exclude <shine-id> 1.0.5 To prevent a moon to be synchronized with other players.
  • <shine-id> The unique ID for an individual shine (moon) in the game.
shine include <shine-id> 1.0.5 To no longer prevent a moon to be synchronized with other players.
  • <shine-id> The unique ID for an individual shine (moon) in the game.
dscrestart 1.0.2 Restarts the Discord bot.
restartserver 1.0.3 Stops the server and restarts it again in a new process. This doesn't work well with docker, because when its main process stops, the whole docker container will be stopped.
exit quit q Stops the server.
Setting up a Discord bot

The aim of this is that the SMOO server connects to your private Discord server as a bot. It can then send logs to a dedicated logs channel and receive commands from you or someone else. (This might be way easier to use in remote scenarios than to SSH to the server and attach the CLI to the server process.)

Create an application

Go to discord.com/developers/applications, create a New Application and give it a name (e.g. SMOO Server).

Create a bot

Navigate to the Bot section of the new application and Add Bot. Change its username to one you like and maybe add a nice avatar (you'll see this in Discord). Uncheck the Public Bot setting that is enabled by default. Also make sure that Message Content Intent is enabled, if you want to send commands to the bot.

Generate a bot token

More importantly is that we call Reset Token for the bot. This will generate a new secret token that we need to connect the bot to our SMOO server. Copy the displayed token and paste it into the settings.json of the server (it goes to Discord > Token and needs to be surrounded by double quotes). The token is only displayed once, if you forgot to copy it or lose it later, you can always get back here and use Reset Token to generate a new token (the old one will become invalid by doing this).

Add the application to a server

Navigate to the OAuth2 > URL Generator section of the application and select the bot scope and nothing else. At the bottom there will now be a generated URL. Copy the generated URL and paste it into your address bar. On the opened site you need to authorize your Discord application to access your Discord account. To do so you'll have to to select a Discord server that it shall be granted access to. To confirm the authorization click on Authorize.

Only servers that you have the Manage Server permission for are shown. You should select your own private Discord server for this, that only you have access to (otherwise others can send commands to the SMOO server). If you don't have one yet, just create one, it is free: simply click on the green plus button at the end of your server list.

Create an admin channel

Create a new channel on the Discord Server where the bot shall write its log messages to and receive commands from. We'll need to give the channel ID to the SMOO server to link them, but channel IDs normally aren't shown anywhere within Discord. To achieve this, the Developer Mode needs to be enabled first in the Discord app settings (under User Settings > App Settings > Advanced). Once that is enabled, we can right click on the channel and choose Copy ID.

Create a moderator channel Optional

Create a new channel on the Discord Server where the bot shall receive commands from. As with the admin channel we need to give the channel ID to the SMOO server to link them.

Channel permissions

The bot requires the following permissions for the channel(s):

  • General Permissions > View Channel
  • Text Permissions > Send Messages
  • Text Permissions > Read Message History (to receive commands)

Configure the server
"Discord": {
  "Token": "MTAwND...TI0c",
  "Prefix": "$",
  "CommandChannel": "993864963574140002",
  "LogChannel": "993864963574140001"
}

Now that we have set everything else up and have the bot token and the channel IDs we need to enter them into the settings.json. After changing the settings.json we either need to restart the SMOO server or send it the loadsettings command.

The admin channel ID goes into the LogChannel setting, and the moderator channel ID into the CommandChannel setting. The difference between both channels is, that the command channel won't receive the server log. But both channels can send commands to the server.

If everything is set up correctly, the Discord bot should now be shown as online on the Discord server. You can send the bot commands via direct messages or write them into channels the bot can read. The commands need to start with the prefix that is configured in the settings.json. For example list becomes $list with the default "$" prefix.

Hosting behind a router

The router in your network is the device that manages your connection to the internet. Among other things, your router acts as a security barrier to prevent evil actors on the internet to access your devices directly. Because of that, when someone on the internet (or you yourself) tries to connect to your SMOO server using your public IPv4 address, your router will block that connection attempt.

Port Forwarding

In order to allow the connections, you'll need to tell your router via port forwarding to route all incoming connections for SMOO to your computer running the server software.

Open ports on the internet can be dangerous.
Bots constantly scan for open ports and automatically probe them for known exploit vectors. Bugs in the server software or sloppy programming of it could in theory be used by hackers to gain access to your computer.

For that reason, when the SMOO server is exposed to the public internet, you should not run it directly on your computer. Instead it's advised to use some form of sandboxing/isolation to run it, e.g. with Docker and using an unprivileged user account.

Note: you yourself should use the private or local IPv4 address of your computer to connect to your own server. Using your own public IPv4 address to connect adds unnecessary lag and might be affected by other restrictions.

Firewall settings

Besides port forwarding, the firewall of your computer (or of the router) could also be a cause that prevents connections from reaching your server. Be sure to accept inbound TCP traffic from all source/remote ports for the specific target/local port 1027.

On Windows when starting a server application for the first time, the Windows firewall will inform you that it has blocked some features for the program and asks if access should be allowed. Make sure that you allow it to communicate with private and public networks, otherwise you'll need to allow it manually in the advanced firewall settings of the system or via the command line.

Manually adding a firewall rule to accept SMOO connections using the command line: 

# add permanent rule
netsh advfirewall firewall add rule dir=in action=allow protocol=TCP localport=1027 edge=yes name="SMOO"

# remove permanent rule
netsh advfirewall firewall delete rule name="SMOO"

# add temporary rule with iptables (gone after restart)
sudo iptables -I INPUT -p tcp --dport 1027 -j ACCEPT -m comment --comment "SMOO"

# add permanent rule with ufw
sudo ufw allow in from 0.0.0.0/0 to any port 1027 proto tcp comment "SMOO"

# remove permanent rule with ufw
sudo ufw delete allow in from 0.0.0.0/0 to any port 1027 proto tcp comment "SMOO"
Test ports remotely

To test if the port is forwarded correctly, is not blocked by a firewall, and reach the running server software, you should use a remote port check service to test that it is open:

  • yougetsignal.com
  • portchecker.co
Just change the port number to 1027 and click on Check on one of the websites. It tells you then if the port is open or not and the test itself should trigger log messages in the server output.

An open port means that everything works as it should be. If someone is then not able to connect to your server using your public IPv4 address that most likely implies a problem on their end. Common causes: using the reconnect feature, entering the wrong IPv4 address or port, or not having configured the emulator correctly.

A closed port on the other hand is a strong indicator that the server isn't reachable from the internet. Double check all port forwarding and firewall settings and that you have your own public IPv4 address that isn't shared with other customers of your ISP.

Hosting with a virtual private network

If you aren't able to port forward, don't want to port forward for security reasons, don't want to share your public IPv4 address for privacy reasons, or remote hosting is not an option, then using a virtual private network (VPN) service might be your best alternative.

Common VPN network providers (not to be confused with commercial VPN tunnel/proxy providers):

  • ZeroTier
  • Radmin VPN
  • Hamachi

When using these services you install their (usually proprietary) software on your computer. Inside of the software you can create and/or join a private group/team/network, that connects your computer to a VPN with the other members. Every computer connected to that network will have an additional VPN IP address with which the others can communicate with them.

Only join a VPN with people you trust.
Joining the same network gives other members a more direct access to your computer than with using port forwarding behind a router. What normally is only limited to a single port that you select and allow individually, is now full network access to your whole computer with all of its services.

For your own security, make sure that you update your system regulary, disable services that they should have no access to, and do not under any circumstance disable your firewall while connected to a VPN with strangers.

For SMOO one of the computers in that VPN will need to run the server software. The person running it should use the private or local IPv4 address of their computer to connect to their own server as usual.

The other computers connected to the VPN will be able to connect to the server using the private VPN IPv4 address of the computer running the server.

Playing with a Nintendo Switch

The problem is, that this out of the box only works with emulators, because there is no VPN client that runs on a Nintendo Switch. For that reason, if only one person wants to play with a Switch, they should be the one running the server, so that they connect to their own server using the private IPv4 address of their computer within their home network.

But if multiple persons from different locations want to play with a Switch, that approach doesn't work anymore. In that case additional Switch players that aren't hosting the server need to configure port forwarding on their computers (not on routers) that are connected to the VPN. That way the Switch will not connect to the server directly but to the private IPv4 address within the home network of the computer connected to the VPN, which will then port forward the connection to the server over the VPN.

Manually port forward using the command line (replace ${server_vpn_ip} with the private VPN IPv4 address of the computer hosting the server): 

# add permanent rule (also needs a firewall rule for port 1027)
netsh interface portproxy add v4tov4 listenaddress=0.0.0.0 listenport=1027 connectaddress=${server_vpn_ip} connectport=1027

# remove permanent rule
netsh interface portproxy delete v4tov4 listenaddress=0.0.0.0 listenport=1027

# run a program to port forward (also needs a firewall rule for port 1027)
socat TCP4-LISTEN:1027,fork TCP4:${server_vpn_ip}:1027

# add temporary rules with iptables (gone after restart)
echo 1 | sudo tee /proc/sys/net/ipv4/ip_forward
sudo iptables -I PREROUTING  -t nat -p tcp --dport 1027 -j DNAT --to-destination ${server_vpn_ip}:1027 -m comment --comment "SMOO"
sudo iptables -I POSTROUTING -t nat -p tcp --dport 1027 -d ${server_vpn_ip} -j MASQUERADE -m comment --comment "SMOO"
sudo iptables -I FORWARD -p tcp --dport 1027 -d ${server_vpn_ip} -m state --state NEW,ESTABLISHED -j ACCEPT -m comment --comment "SMOO"
# what this does:
# 1. enable port forwarding on this system
# 2. change the destination address from the PC to the VPN server
# 3. change the source address of the Switch to that of the PC (to get replies back)
# 4. allow this specific port forwarding
